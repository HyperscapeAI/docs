## Overview

The Quest System implements OSRS-style quest progression with dialogue-driven quest starts, multi-stage objectives, and completion rewards. Quests are defined in JSON manifests and tracked in the database with full audit logging.

**Key Features:**
- Manifest-driven quest definitions
- Multi-stage quest progression (dialogue, kill, gather, interact)
- HMAC kill token validation (prevents spoofing)
- Quest journal UI with color-coded status
- XP lamp rewards with skill selection
- Database persistence with audit trail
- Rate limiting and security validation

### Database Schema

```sql
-- Quest Progress Table
CREATE TABLE quest_progress (
  id SERIAL PRIMARY KEY,
  playerId TEXT NOT NULL REFERENCES characters(id) ON DELETE CASCADE,
  questId TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'not_started',
  currentStage TEXT,
  stageProgress JSONB DEFAULT '{}',
  startedAt BIGINT,
  completedAt BIGINT,
  UNIQUE(playerId, questId)
);

-- Quest Audit Log (immutable security trail)
CREATE TABLE quest_audit_log (
  id SERIAL PRIMARY KEY,
  playerId TEXT NOT NULL,
  questId TEXT NOT NULL,
  action TEXT NOT NULL,  -- 'started', 'progressed', 'completed'
  questPointsAwarded INTEGER DEFAULT 0,
  stageId TEXT,
  stageProgress JSONB DEFAULT '{}',
  timestamp BIGINT NOT NULL,
  metadata JSONB DEFAULT '{}'
);

-- Quest Points Column
ALTER TABLE characters ADD COLUMN questPoints INTEGER DEFAULT 0 NOT NULL;
```

```json
      {

    }
  }

```

### Quest Definition Properties

| Property | Type | Description |
|----------|------|-------------|
| `id` | string | Unique quest identifier (snake_case) |
| `name` | string | Display name shown in journal |
| `description` | string | Quest summary |
| `difficulty` | string | `novice`, `intermediate`, `experienced`, `master` |
| `questPoints` | number | Quest points awarded on completion |
| `replayable` | boolean | Whether quest can be repeated |
| `requirements` | object | Prerequisites (quests, skills, items) |
| `startNpc` | string | NPC ID that starts the quest |
| `stages` | array | Quest stages (see below) |
| `onStart` | object | Items granted when quest starts |
| `rewards` | object | Rewards on completion |

### Stage Types

| Type | Purpose | Properties |
|------|---------|------------|
| **dialogue** | Talk to NPC | `description` |
| **kill** | Kill mobs | `target` (mob type), `count` |
| **gather** | Collect items | `target` (item ID), `count` |
| **interact** | Use stations | `target` (station type), `count` |

## Quest Flow

### 1. Quest Request

Player talks to NPC → DialogueSystem checks for quest overrides → Emits `QUEST_START_CONFIRM`:

```typescript
// DialogueSystem checks quest status and shows appropriate dialogue
const questSystem = world.getSystem("quest") as QuestSystem;
const status = questSystem.getQuestStatus(playerId, questId);

// Priority: ready_to_complete > in_progress > completed > default
if (status === "ready_to_complete" && overrides.ready_to_complete) {
  entryNodeId = overrides.ready_to_complete;
} else if (status === "in_progress" && overrides.in_progress) {
  entryNodeId = overrides.in_progress;
}
```

### 2. Quest Accept

Client shows QuestStartScreen → Player clicks Accept → Server validates and starts quest:

```typescript
// Server handler (quest.ts)
export async function handleQuestAccept(socket, data, world) {
  const playerId = getPlayerId(socket);
  
  // Rate limit check (3 requests/sec)
  if (!getQuestAcceptRateLimiter().check(playerId)) return;
  
  // Validate quest ID format
  if (!isValidQuestId(data.questId)) return;
  
  // Start quest (validates requirements, grants starting items)
  const success = await questSystem.startQuest(playerId, data.questId);
}
```

### 3. Quest Progress

QuestSystem subscribes to game events and tracks progress:

```typescript
// Kill tracking with HMAC validation
this.subscribe(EventType.NPC_DIED, (data) => {
  const { killedBy, mobType, killToken, timestamp } = data;
  
  // Validate kill token (prevents spoofing)
  if (!validateKillToken(mobId, killedBy, timestamp, killToken)) {
    this.logger.warn("Invalid kill token - possible spoof attempt");
    return;
  }
  
  // Update progress
  const progress = state.activeQuests.get(questId);
  progress.stageProgress.kills = (progress.stageProgress.kills || 0) + 1;
  
  // Check if objective complete
  if (progress.stageProgress.kills >= stage.count) {
    progress.status = "ready_to_complete";
    // Emit chat message
  }
});
```

### 4. Quest Completion

Player returns to NPC → DialogueSystem triggers `completeQuest` effect:

```typescript
// Dialogue effect (DialogueSystem.ts)
case "completeQuest": {
  const questId = params[0];
  const questSystem = this.world.getSystem("quest") as QuestSystem;
  await questSystem.completeQuest(playerId, questId);
  break;
}
```

Quest completion is atomic (database transaction):

```typescript
// QuestRepository.completeQuestWithPoints()
await this.db.transaction(async (tx) => {
  // Mark quest as completed
  await tx.update(schema.questProgress)
    .set({ status: "completed", completedAt: Date.now() })
    .where(and(
      eq(schema.questProgress.playerId, playerId),
      eq(schema.questProgress.questId, questId)
    ));
  
  // Award quest points
  if (questPoints > 0) {
    await tx.update(schema.characters)
      .set({ questPoints: sql`${schema.characters.questPoints} + ${questPoints}` })
      .where(eq(schema.characters.id, playerId));
  }
  
  // Audit log
  await tx.insert(schema.questAuditLog).values({
    playerId, questId, action: "completed",
    questPointsAwarded: questPoints, timestamp: Date.now()
  });
});
```

## Quest Status

Quests have 4 possible statuses:

| Status | Description | Color |
|--------|-------------|-------|
| `not_started` | Quest not yet accepted | Red |
| `in_progress` | Quest active, objective incomplete | Yellow |
| `ready_to_complete` | Objective met, return to NPC | Yellow |
| `completed` | Quest finished | Green |

<Info>
`ready_to_complete` is a **derived status** computed at runtime when `status === "in_progress"` AND the current stage objective is met. It's not stored in the database to prevent inconsistency.
</Info>

## Security Features

### HMAC Kill Token Validation

Prevents quest progress manipulation via spoofed `NPC_DIED` events:

```typescript
// Server generates token when mob dies (CombatSystem)
import { generateKillToken } from '@hyperscape/shared/utils/game/KillTokenUtils';

const timestamp = Date.now();
const killToken = generateKillToken(mobId, killedBy, timestamp);

world.emit(EventType.NPC_DIED, {
  killedBy, mobType, mobId, timestamp, killToken
});
```

```typescript
// QuestSystem validates token before counting kill
import { validateKillToken } from '@hyperscape/shared/utils/game/KillTokenUtils';

if (!validateKillToken(mobId, killedBy, timestamp, killToken)) {
  this.logger.warn("Invalid kill token - possible spoof attempt");
  return; // Reject spoofed progress
}
```

**Implementation:**
- Uses HMAC-SHA256 with server-side secret
- Tokens include: `mobId`, `killedBy`, `timestamp`
- 5-second validation window
- Server-only (uses Node.js crypto module)

### Rate Limiting

Quest network handlers are rate-limited to prevent abuse:

| Handler | Rate Limit | Purpose |
|---------|------------|---------|
| `getQuestList` | 5 req/sec | Prevent UI spam |
| `getQuestDetail` | 10 req/sec | Prevent detail spam |
| `questAccept` | 3 req/sec | Prevent accept spam |

### Input Validation

All quest IDs are validated using `isValidQuestId()`:

```typescript
export const MAX_QUEST_ID_LENGTH = 64;
export const QUEST_ID_PATTERN = /^[a-z][a-z0-9_]{0,63}$/;

export function isValidQuestId(id: unknown): id is string {
  return (
    typeof id === "string" &&
    id.length > 0 &&
    id.length <= MAX_QUEST_ID_LENGTH &&
    QUEST_ID_PATTERN.test(id)
  );
}
```

## XP Lamp System

Quest rewards can include XP lamps that let players choose which skill receives XP:

### XP Lamp Item

```json
{
  "id": "xp_lamp_1000",
  "name": "XP Lamp (1000 XP)",
  "type": "consumable",
  "useEffect": {
    "type": "xp_lamp",
    "xpAmount": 1000
  },
  "inventoryActions": ["Rub", "Drop", "Examine"],
  "description": "Grants 1000 XP to a skill of your choice",
  "tradeable": false
}
```

### Usage Flow

1. Player right-clicks lamp → Selects "Rub"
2. `SkillSelectModal` opens showing all 13 skills with current levels
3. Player clicks a skill
4. Server validates and grants XP:

```typescript
// Server handler (inventory.ts)
export async function handleXpLampUse(socket, data, world) {
  // Validate skill ID
  if (!VALID_SKILL_IDS.has(data.skillId)) return;
  
  // Validate XP amount matches item definition
  const lampData = getItem(data.itemId);
  if (lampData?.useEffect?.xpAmount !== data.xpAmount) return;
  
  // Remove lamp from inventory
  world.emit(EventType.INVENTORY_ITEM_REMOVED, {
    playerId, itemId, quantity: 1, slot
  });
  
  // Grant XP
  world.emit(EventType.SKILLS_XP_GAINED, {
    playerId, skill: data.skillId, amount: data.xpAmount
  });
}
```

## Performance Optimizations

### O(1) Stage Lookup Caches

Quest stages are cached in Maps for fast lookups:

```typescript
// Pre-allocated stage lookup caches (per quest)
private _stageCaches: Map<string, Map<string, QuestStage>> = new Map();

private getStageCache(questId: string): Map<string, QuestStage> {
  let cache = this._stageCaches.get(questId);
  if (!cache) {
    const definition = this.questDefinitions.get(questId);
    cache = new Map(definition.stages.map(s => [s.id, s]));
    this._stageCaches.set(questId, cache);
  }
  return cache;
}
```

**Impact:** O(n) → O(1) for stage lookups in hot paths (NPC_DIED events)

### Object Spread Elimination

Direct mutation replaces object spreads in hot paths:

```typescript
// Before: Allocates new object on every kill
progress.stageProgress = {
  ...progress.stageProgress,
  [stage.target]: currentKills
};

// After: Direct mutation (zero allocation)
progress.stageProgress[stage.target] = currentKills;
```

### Log Verbosity Reduction

```typescript
// Debug-level for frequent events
this.logger.debug(`NPC_DIED: killedBy=${killedBy}, mobType=${mobType}`);

// Info-level only for milestones
this.logger.info(`Quest completed: ${questId} by ${playerId}`);
```

## Best Practices

1. **Use descriptive IDs**: `goblin_slayer` not `quest1`
2. **Validate quest IDs**: Always use `isValidQuestId()` in handlers
3. **Atomic completion**: Use `completeQuestWithPoints()` for database consistency
4. **Security-first**: Validate all inputs, use kill tokens for combat quests
5. **Test thoroughly**: Add integration tests for new quest types
6. **Audit logging**: All quest state changes are logged for security auditing

## Troubleshooting

**Quest not appearing in journal:**
- Check `quests.json` syntax (must be valid JSON)
- Verify quest ID matches in dialogue overrides
- Restart server to reload manifests

**Quest progress not tracking:**
- Check stage `target` matches mob type/item ID exactly
- Verify kill tokens are being generated (server-side only)
- Check quest audit log for progress events

**Quest completion fails:**
- Ensure all stage objectives are met
- Check dialogue effect syntax: `completeQuest <questId>`
- Verify player meets requirements

**Database errors:**
- Run migrations: `cd packages/server && bunx drizzle-kit migrate`
- Check PostgreSQL is running: `docker ps | grep postgres`
