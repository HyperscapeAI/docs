## Overview

Hyperscape uses manifest-driven design where game content is defined in TypeScript data files rather than hardcoded in logic. This enables content creation without modifying game systems.

## Design Philosophy

### Separation of Concerns

| Layer | Responsibility |
|-------|----------------|
| **Manifests** | Content definitions (what exists) |
| **Systems** | Game logic (how things work) |
| **Entities** | Runtime instances |

### Benefits

- **Content creators** can add items, NPCs, areas without deep coding
- **Designers** iterate quickly on balance
- **Developers** focus on systems, not data
- **Modders** can extend content easily

## Manifest Files

Manifests are split between TypeScript data files and JSON manifests:

| File | Content |
|------|---------|
| `npcs.ts` | Mobs and NPCs |
| `items.ts` | Equipment, resources, consumables |
| `banks-stores.ts` | Shop inventories |
| `world-areas.ts` | Zones and regions |
| `world-structure.ts` | World layout |
| `avatars.ts` | Character models |
| `playerEmotes.ts` | Emote animations |
| `equipment-requirements.json` | Level requirements for gear |
| `equipment-stats.json` | Stat bonuses for equipment |

## Manifest Structure

### NPCs (`npcs.ts`)

NPC data is loaded from JSON manifests at runtime by DataManager:

```typescript
// From packages/shared/src/data/npcs.ts (lines 1-21)
/**
 * NPC Database
 *
 * ALL NPC data is loaded from JSON manifests at runtime by DataManager.
 * This keeps NPC definitions data-driven and separate from code.
 *
 * Available 3D model types (in /assets/world/forge/):
 * - goblin/goblin_rigged.glb     → Used for goblins
 * - thug/thug_rigged.glb         → Used for bandits
 * - human/human_rigged.glb       → Used for guards, knights, warriors
 * - troll/troll_rigged.glb       → Used for hobgoblins
 * - imp/imp_rigged.glb           → Used for dark warriors
 *
 * To add new NPCs:
 * 1. Add entry to world/assets/manifests/npcs.json
 * 2. Use one of the existing modelPath types above
 * 3. OR generate new model in 3D Asset Forge
 * 4. Restart server to reload manifests
 */

// NPC Database - Populated at runtime from JSON manifests
export const ALL_NPCS: Map<string, NPCData> = new Map();
```

<Info>
  NPC definitions are in `world/assets/manifests/npcs.json`, not hardcoded in TypeScript.
</Info>

### Items (`items.ts`)

Items are loaded from JSON manifests similar to NPCs:

```typescript
// From packages/shared/src/data/items.ts (lines 1-25)
/**
 * Item Database
 *
 * Items are loaded from world/assets/manifests/items.json by DataManager.
 * This file provides the empty Map that gets populated at runtime.
 *
 * To add new items:
 * 1. Add entries to world/assets/manifests/items.json
 * 2. Generate 3D models in 3D Asset Forge (optional)
 * 3. Restart the server to reload manifests
 */

// Item Database - Populated by DataManager
export const ITEMS: Map<string, Item> = new Map();

// Helper functions
export function getItem(itemId: string): Item | null {
  return ITEMS.get(itemId) || null;
}

export function getItemsByType(type: ItemType): Item[] {
  return Array.from(ITEMS.values()).filter((item) => item.type === type);
}

// Shop items available for purchase
export const SHOP_ITEMS = ["bronze_hatchet", "fishing_rod", "tinderbox", "arrows"];
```

### Recipe Manifests (`recipes/`)

Smithing, cooking, and other processing skills use recipe manifests:

**Smelting Recipe** (`recipes/smelting.json`):
```json
{
  "recipes": [
    {
      "output": "bronze_bar",
      "inputs": [
        { "item": "copper_ore", "amount": 1 },
        { "item": "tin_ore", "amount": 1 }
      ],
      "level": 1,
      "xp": 6.25,
      "ticks": 4,
      "successRate": 1.0
    }
  ]
}
```

**Smithing Recipe** (`recipes/smithing.json`):
```json
{
  "recipes": [
    {
      "output": "bronze_sword",
      "bar": "bronze_bar",
      "barsRequired": 1,
      "level": 4,
      "xp": 12.5,
      "ticks": 4,
      "category": "weapons"
    }
  ]
}
```

## Data Providers

### DataManager

The `DataManager` class in `packages/shared/src/data/DataManager.ts` loads all manifests from JSON files and populates runtime data structures:

```typescript
import { dataManager } from '@hyperscape/shared';

// Initialize (loads all manifests)
await dataManager.initialize();

// Access loaded data via global Maps
import { ITEMS, ALL_NPCS } from '@hyperscape/shared';
const item = ITEMS.get("bronze_sword");
const npc = ALL_NPCS.get("goblin");
```

### ProcessingDataProvider

Provides runtime access to cooking, firemaking, smelting, and smithing recipes:

```typescript
import { processingDataProvider } from '@hyperscape/shared';

// Smelting
const smeltingData = processingDataProvider.getSmeltingData('bronze_bar');
const canSmelt = processingDataProvider.isSmeltableBar('iron_bar');
const availableBars = processingDataProvider.getSmeltableBarsFromInventory(inventory, level);

// Smithing
const recipe = processingDataProvider.getSmithingRecipe('bronze_sword');
const recipes = processingDataProvider.getSmithingRecipesForBar('bronze_bar');
const available = processingDataProvider.getSmithableItemsWithAvailability(inventory, level);

// Cooking
const cookingData = processingDataProvider.getCookingData('raw_shrimp');
const isCookable = processingDataProvider.isCookable('raw_trout');

// Firemaking
const firemakingData = processingDataProvider.getFiremakingData('logs');
const isBurnable = processingDataProvider.isBurnableLog('oak_logs');
```

### TierDataProvider

Provides tier-based level requirements for equipment and tools:

```typescript
import { TierDataProvider } from '@hyperscape/shared';

// Get requirements for a tiered item
const requirements = TierDataProvider.getRequirements({
  id: 'steel_sword',
  type: 'weapon',
  tier: 'steel',
  equipSlot: 'weapon',
  attackType: 'MELEE'
});
// Returns: { attack: 5 }

// Get tier data directly
const tierData = TierDataProvider.getTierData('melee', 'rune');
// Returns: { attack: 40, defence: 40 }
```

### StationDataProvider

Provides configuration for world stations (anvils, furnaces, ranges):

```typescript
import { stationDataProvider } from '@hyperscape/shared';

// Get station configuration
const anvilData = stationDataProvider.getStationData('anvil');
// Returns: { type, name, model, modelScale, modelYOffset, examine }

// Get model path for 3D rendering
const modelPath = stationDataProvider.getModelPath('furnace');
// Returns: "asset://models/furnace/furnace.glb"

// Get examine text
const examineText = stationDataProvider.getExamineText('anvil');
// Returns: "An anvil for smithing metal bars into weapons and tools."
```

## Adding Content

### Step 1: Edit JSON Manifest

Add your content to the appropriate JSON manifest file in `packages/server/world/assets/manifests/`.

**Example: Adding a new smithing recipe**

Edit `packages/server/world/assets/manifests/recipes/smithing.json`:

```json
{
  "recipes": [
    {
      "output": "mithril_platebody",
      "bar": "mithril_bar",
      "barsRequired": 5,
      "level": 68,
      "xp": 250,
      "ticks": 4,
      "category": "armor"
    }
  ]
}
```

### Step 2: Restart Server

JSON manifests are loaded at server startup. Restart to apply changes:

```bash
# Stop server (Ctrl+C)
bun run dev
```

### Step 3: Verify

Check the game to ensure content appears correctly. The smithing interface should show your new recipe.

## Validation

### JSON Manifest Validation

JSON manifests are validated at runtime by DataManager:

- **Schema validation**: Required fields checked on load
- **Duplicate detection**: Duplicate item IDs cause errors
- **Atomic loading**: All required files must exist (e.g., all 5 item category files)
- **Fallback support**: Falls back to legacy single-file format if directory loading fails

### TypeScript Data File Validation

TypeScript data files get compile-time validation:

- **Type checking**: Invalid fields caught at compile time
- **Autocomplete**: IDE suggestions for valid properties
- **Required fields**: Missing fields cause build errors
- **References**: TypeScript catches invalid itemId/npcId references

<Warning>
  Invalid JSON manifests will cause server startup to fail with descriptive errors. Check server logs for details.
</Warning>

## Best Practices

1. **Use descriptive IDs**: `bronze_sword` not `sword1`
2. **Follow naming conventions**: snake_case for IDs
3. **Organize by category**: Use the directory structure (items/, recipes/, gathering/)
4. **Test after changes**: Verify in-game before committing
5. **Keep data flat**: Avoid deep nesting in manifest structures
6. **Use tier system**: Leverage TierDataProvider for equipment requirements instead of hardcoding
7. **Validate JSON**: Use a JSON validator before committing to catch syntax errors

## Manifest Loading Order

DataManager loads manifests in this order:

1. **Tier requirements** (`tier-requirements.json`) - Needed for item normalization
2. **Items** (`items/` directory or `items.json` fallback)
3. **NPCs** (`npcs.json`)
4. **Gathering resources** (`gathering/*.json`)
5. **Recipe manifests** (`recipes/*.json`)
6. **Skill unlocks** (`skill-unlocks.json`)
7. **Stations** (`stations.json`)
8. **World areas** (`world-areas.json`)
9. **Stores** (`stores.json`)

This order ensures dependencies are loaded before dependent data (e.g., tier requirements before items).
