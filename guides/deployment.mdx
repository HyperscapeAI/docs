## Deployment Overview

Hyperscape uses a split deployment architecture optimized for scalability and performance:

- **Frontend**: Cloudflare Pages (hyperscape.club)
- **Game Server**: Railway (hyperscape-production.up.railway.app)
- **Database**: PostgreSQL via Railway or Neon
- **Assets/CDN**: Cloudflare R2 (assets.hyperscape.club)

This architecture separates static content (frontend) from dynamic game logic (server) and leverages CDN edge caching for assets.

### Production URLs

| Component | URL | Purpose |
|-----------|-----|---------|
| Frontend | https://hyperscape.club | Client application (Cloudflare Pages) |
| Game Server | https://hyperscape-production.up.railway.app | WebSocket + HTTP API (Railway) |
| Assets CDN | https://assets.hyperscape.club | Game assets (Cloudflare R2) |

### Architecture Benefits

- **Global CDN**: Assets served from edge locations worldwide
- **Auto-scaling**: Railway handles server scaling automatically
- **Zero-downtime deploys**: Cloudflare Pages atomic deployments
- **Cost-effective**: R2 has no egress fees

## Railway Deployment (Game Server)

Railway hosts the game server with automatic deployments from GitHub.

### Automated Deployment

The repository includes a GitHub Actions workflow that automatically deploys to Railway on every push to `main`:

```yaml
# .github/workflows/deploy-railway.yml
# Triggers on changes to server, shared, or client packages
```

**What happens on push:**
1. GitHub Actions triggers Railway deployment via GraphQL API
2. Railway builds using Nixpacks configuration
3. Builds shared package → server package → client package
4. Copies client build to server's `public/` directory
5. Fetches manifests from CDN at startup
6. Deploys to production with health checks

### Manual Railway Setup

<Steps>
  <Step title="Create Railway project">
    1. Go to [railway.app](https://railway.app)
    2. Create new project from GitHub repo
    3. Select `HyperscapeAI/hyperscape`
  </Step>
  
  <Step title="Configure build settings">
    Railway uses `nixpacks.toml` and `railway.server.json` for configuration:
    
    - **Builder**: Nixpacks (auto-detected)
    - **Start command**: `cd packages/server && bun dist/index.js`
    - **Health check**: `/status` endpoint
    - **Watch patterns**: `packages/shared/**`, `packages/server/**`, `packages/client/**`
  </Step>
  
  <Step title="Add PostgreSQL database">
    1. In Railway dashboard, click "New" → "Database" → "PostgreSQL"
    2. Railway automatically sets `DATABASE_URL` environment variable
    3. No manual configuration needed
  </Step>
  
  <Step title="Set environment variables">
    Required variables:
    ```bash
    PRIVY_APP_ID=your-app-id
    PRIVY_APP_SECRET=your-app-secret
    PUBLIC_CDN_URL=https://assets.hyperscape.club
    JWT_SECRET=your-random-secret-32-chars
    NODE_ENV=production
    ```
    
    Optional variables:
    ```bash
    ADMIN_CODE=your-admin-code
    LIVEKIT_API_KEY=your-livekit-key
    LIVEKIT_API_SECRET=your-livekit-secret
    ```
  </Step>
  
  <Step title="Deploy">
    Push to `main` branch or click "Deploy" in Railway dashboard.
    
    Monitor deployment:
    - Build logs show package compilation
    - Health check validates `/status` endpoint
    - WebSocket connections tested automatically
  </Step>
</Steps>

### Railway Configuration Files

**nixpacks.toml** - Build configuration:
```toml
[phases.setup]
aptPkgs = ["python3", "make", "g++", "pkg-config", "libcairo2-dev"]

[phases.build]
cmds = [
  "bun run build:shared",
  "bun run build:server",
  "mkdir -p packages/server/world/assets/manifests"
]

[start]
cmd = "cd packages/server && bun dist/index.js"

[variables]
CI = "true"
SKIP_ASSETS = "true"
NODE_ENV = "production"
```

**railway.server.json** - Service configuration:
```json
{
  "build": {
    "builder": "NIXPACKS",
    "nixpacksConfigPath": "nixpacks.toml"
  },
  "deploy": {
    "startCommand": "cd packages/server && bun dist/index.js",
    "healthcheckPath": "/status",
    "restartPolicyType": "ON_FAILURE"
  }
}
```

### Troubleshooting Railway Deployments

**Build fails with "lockfile frozen" error:**
```bash
# Regenerate lockfile locally
bun install
git add bun.lock
git commit -m "chore: update bun.lock"
git push
```

**Frontend not loading (404 on index.html):**
- Check build logs for client build step
- Verify `cp -r dist/* public/` command succeeded
- Check `/debug/public` endpoint to see directory contents

**WebSocket connection fails:**
- Verify `PUBLIC_WS_URL` in client points to Railway domain
- Check CORS allowlist includes your frontend domain
- Ensure Railway exposes WebSocket port (default: 5555)

## Cloudflare Pages Deployment (Frontend)

Cloudflare Pages hosts the game client with automatic deployments from GitHub.

### Automatic Deployment

Cloudflare Pages is connected directly to the GitHub repository:

1. **Push to `main`** → Automatic production deployment
2. **Open PR** → Automatic preview deployment at `*.hyperscape.pages.dev`
3. **Merge PR** → Preview becomes production

**No manual deployment needed** - Cloudflare handles everything via GitHub integration.

### Manual Cloudflare Pages Setup

<Steps>
  <Step title="Create Cloudflare Pages project">
    1. Go to [Cloudflare Dashboard](https://dash.cloudflare.com) → Pages
    2. Click "Create a project" → "Connect to Git"
    3. Select `HyperscapeAI/hyperscape` repository
  </Step>
  
  <Step title="Configure build settings">
    - **Framework preset**: None (custom Vite build)
    - **Build command**: `cd packages/client && bun install && bun run build`
    - **Build output directory**: `packages/client/dist`
    - **Root directory**: `/` (monorepo root)
    - **Node version**: 22
  </Step>
  
  <Step title="Set environment variables">
    In Pages dashboard → Settings → Environment variables:
    
    **Production:**
    ```bash
    PUBLIC_PRIVY_APP_ID=your-app-id
    PUBLIC_API_URL=https://hyperscape-production.up.railway.app
    PUBLIC_WS_URL=wss://hyperscape-production.up.railway.app/ws
    PUBLIC_CDN_URL=https://assets.hyperscape.club
    PUBLIC_APP_URL=https://hyperscape.club
    ```
    
    **Preview (optional):**
    Same as production, or use preview-specific values for testing.
  </Step>
  
  <Step title="Configure custom domain">
    1. Pages → Custom domains → Add domain
    2. Add `hyperscape.club` and `www.hyperscape.club`
    3. Update DNS records as instructed
    4. SSL certificates are provisioned automatically
  </Step>
</Steps>

### CORS Configuration

The server automatically allows Cloudflare Pages domains:

```typescript
// packages/server/src/startup/http-server.ts
const allowedOrigins = [
  "https://hyperscape.club",
  "https://www.hyperscape.club",
  "https://hyperscape.pages.dev",
  /^https?:\\/\\/.+\\.hyperscape\\.pages\\.dev$/,  // Preview deployments
];
```

Preview deployments (e.g., `abc123.hyperscape.pages.dev`) are automatically allowed via regex pattern.

## CDN & Assets Setup

### Cloudflare R2 (Production)

Hyperscape uses Cloudflare R2 for asset storage with global CDN distribution.

<Steps>
  <Step title="Create R2 bucket">
    1. Go to Cloudflare dashboard → R2
    2. Create bucket named `hyperscape-assets`
    3. Enable public access
  </Step>

  <Step title="Upload assets">
    Use the sync script to upload assets:
    
    ```bash
    # Set Cloudflare credentials
    export CLOUDFLARE_ACCOUNT_ID=your-account-id
    export CLOUDFLARE_API_TOKEN=your-api-token
    
    # Upload assets to R2
    bun run sync:r2
    ```
  </Step>

  <Step title="Configure custom domain">
    1. In R2 bucket settings, add custom domain: `assets.hyperscape.club`
    2. Cloudflare auto-configures DNS and SSL
    3. Set `PUBLIC_CDN_URL=https://assets.hyperscape.club` in both server and client
  </Step>
</Steps>

## CDN Setup (Assets)

### Production: Cloudflare R2

Hyperscape uses Cloudflare R2 for asset storage with automatic uploads via GitHub Actions.

**Automatic Asset Deployment:**

The `.github/workflows/deploy-cloudflare.yml` workflow automatically uploads assets to R2 when:
- Manifests change in `packages/server/world/assets/manifests/**`
- Asset files change in `assets/**`

**What gets uploaded:**
- **Manifests** (JSON files) → `manifests/*.json`
- **Models** (GLB/GLTF) → `models/**/*.glb`
- **Audio** (MP3/OGG) → `audio/**/*.mp3`
- **Textures** (PNG/JPG) → `textures/**/*.png`
- **WASM binaries** → `*.wasm`

**R2 Configuration:**
```bash
# In Cloudflare Dashboard → R2
Bucket name: hyperscape-assets
Public access: Enabled via custom domain
Custom domain: assets.hyperscape.club
```

**Required GitHub Secrets:**
- `CLOUDFLARE_API_TOKEN` - API token with R2 write permissions

### Development: Local Docker CDN

For local development, use the included nginx CDN:

```bash
bun run cdn:up          # Start CDN container
bun run cdn:down        # Stop CDN container
bun run cdn:restart     # Force restart
```

This starts a Docker container serving assets from `packages/server/world/assets/` on port 8080.

**CDN Commands:**
```bash
bun run cdn:up        # Start CDN container
bun run cdn:down      # Stop CDN container
bun run cdn:restart   # Force restart (rebuild container)
bun run cdn:watch     # Start with file watching
```

### Manifest Fetching System

**New in v1.0:** The server automatically fetches manifests from the CDN at startup instead of bundling them.

**How it works:**
1. Server starts and checks `packages/server/world/assets/manifests/` directory
2. If in production or manifests are missing, fetches from `PUBLIC_CDN_URL`
3. Downloads all manifest JSON files (items, npcs, resources, etc.)
4. Caches locally for faster subsequent starts
5. Compares content hashes to avoid unnecessary updates

**Manifest files fetched:**
- `items.json` - Item definitions
- `npcs.json` - NPC and mob data
- `resources.json` - Gathering resources
- `tools.json` - Tool definitions
- `biomes.json` - Biome configurations
- `world-areas.json` - World zones
- `stores.json` - Shop inventories
- `music.json` - Music track metadata
- `vegetation.json` - Vegetation placement
- `buildings.json` - Building definitions

**Configuration:**
```typescript
// packages/server/src/startup/config.ts
await fetchManifestsFromCDN(CDN_URL, manifestsDir, NODE_ENV);
```

**Behavior:**
- **Development**: Skips fetch if local manifests exist (uses Git LFS assets)
- **Production**: Always fetches from CDN to ensure latest data
- **CI/Test**: Skips fetch if `SKIP_MANIFESTS=true` is set

### Alternative: Self-Hosted CDN

For self-hosted deployments, you can use any static file server:

**Option 1: nginx**
```nginx
server {
  listen 8080;
  root /var/www/hyperscape-assets;
  
  location /manifests/ {
    add_header Cache-Control "public, max-age=300, must-revalidate";
  }
  
  location /models/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }
}
```

**Option 2: AWS S3**
1. Create S3 bucket with public read access
2. Upload `packages/server/world/assets/` contents
3. Set `PUBLIC_CDN_URL=https://your-bucket.s3.amazonaws.com`

**Option 3: Other providers**
- DigitalOcean Spaces
- Backblaze B2
- Wasabi
- Any CDN with object storage

## Production Checklist

### Server (Railway)
- [ ] PostgreSQL database provisioned (Railway or Neon)
- [ ] Environment variables configured in Railway dashboard
- [ ] `PRIVY_APP_ID` and `PRIVY_APP_SECRET` set
- [ ] `JWT_SECRET` generated (32+ characters)
- [ ] `PUBLIC_CDN_URL` points to R2 or CDN
- [ ] `NODE_ENV=production` set
- [ ] Health check endpoint `/status` responding
- [ ] WebSocket connections working on port 5555

### Frontend (Cloudflare Pages)
- [ ] GitHub integration connected
- [ ] Build command configured: `cd packages/client && bun install && bun run build`
- [ ] `PUBLIC_PRIVY_APP_ID` matches server's `PRIVY_APP_ID`
- [ ] `PUBLIC_API_URL` points to Railway server
- [ ] `PUBLIC_WS_URL` points to Railway WebSocket (wss://)
- [ ] `PUBLIC_CDN_URL` points to R2 assets
- [ ] Custom domain configured (hyperscape.club)
- [ ] SSL/TLS enabled (automatic with Cloudflare)

### Assets (Cloudflare R2)
- [ ] R2 bucket created (`hyperscape-assets`)
- [ ] Public access enabled via custom domain
- [ ] Custom domain configured (assets.hyperscape.club)
- [ ] GitHub Actions workflow has `CLOUDFLARE_API_TOKEN` secret
- [ ] Manifests uploaded to `manifests/` prefix
- [ ] WASM files uploaded with correct MIME type
- [ ] CORS headers configured for cross-origin access

### CORS Verification
- [ ] Server allows frontend domain in CORS allowlist
- [ ] Preview deployments (`*.hyperscape.pages.dev`) allowed
- [ ] WebSocket upgrade requests working
- [ ] Asset requests from CDN working cross-origin

### Post-Deployment Testing
- [ ] Visit frontend URL and verify it loads
- [ ] Create character and verify database persistence
- [ ] Test WebSocket connection (check browser console)
- [ ] Verify assets load from CDN (check Network tab)
- [ ] Test authentication flow with Privy
- [ ] Verify manifest fetching in server logs
- [ ] Test gameplay (movement, combat, skills)
- [ ] Check health endpoint: `https://your-server.up.railway.app/status`
